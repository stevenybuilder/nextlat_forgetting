# NL-1 feasibility and dataset audit

**Assessment date:** 2026-08-24  
**Verdict:** two-layer language program scientifically specified, technically
unimplemented, and blocked on separate measured profiles plus budget approval  
**Provenance:** the hash-bound FineWeb-Edu NL-1 declaration remains unchanged; a
new prospective amendment adds TS-1 and makes the two-arm claim rule explicit

## Required language program

The design now uses both language datasets for different, non-interchangeable jobs:

1. **TS-1 / TinyStories parity and positive control.** Reuse the pinned v4
   synthetic-language setup as closely as tractable: GPT versus one-step NextLat,
   100,000 base steps, then the 20 future-token probes for 20,000 steps. This tests
   implementation parity with v4's representational result.
2. **NL-1 / FineWeb-Edu external validation.** Use filtered real-world web text for
   the new geometry--forgetting association after continued pretraining. This tests
   whether the controlled finding triangulates outside generated stories.

Both completed studies are required before claiming the full language
external-validity program in a workshop submission. They cannot rescue controlled
core nulls, and their independent profile gates cannot be traded against each other.
If either is not launched, the report must identify the missing layer rather than
quietly promoting the other.

## What each candidate dataset actually establishes

| Dataset | What it contains | Ground truth available | Pinned NextLat workload | Decision |
| --- | --- | --- | --- | --- |
| TinyStories | 2.7M simple English stories generated by GPT-3.5/GPT-4 | observed future tokens only; no exact conditional or belief state | 8L/768, batch 256, length 256, 100k steps; then 20 probe offsets for 20k steps | **TS-1 required parity/positive-control layer**; still does not answer the natural-data objection alone |
| FineWeb-Edu | filtered real-world Common-Crawl web text selected by an educational classifier trained from Llama-3 annotations; residual duplicates and machine-generated pages may remain | observed text and metadata; no exact predictive state and no guarantee every page is human-authored | paper: 1.3B parameters/100B tokens; repository also supplies 100M-class/10B-token configs | **NL-1 required real-web layer**, at a frozen exploratory 100M-class/2B-token scale |
| Manhattan | random traversals over a real Manhattan street graph, not text | true street graph/intersection state; structured trajectory targets | 48L/384, batch 256, length 256, 400k steps/six epochs | valuable structured world-model test, but not natural-language external validity and too costly here |

The distinction matters. “Synthetic” is not one axis: TinyStories' actual prose is
model-generated; FineWeb-Edu is filtered real-world web text but its quality filter
uses synthetic annotations and the corpus can retain duplicates or machine-generated
pages; Manhattan sequences are generated traversals grounded in a real graph. None
should be represented as more natural or more human than it is.

The official 100M FineWeb launch scripts assume four GPUs. On one 24GB GPU, the
resolved physical microbatch from the unmodified config would be 256 sequences of
1,024 tokens, which is not a plausible fit. NL-1 must preserve the effective batch
with greater gradient accumulation; it cannot claim single-GPU launch parity before
profiling this fallback.

NL-1 explicitly selects WSD and proportionally shortens warmdown for its frozen
2B-token budget. That is a declared new-study deviation, not a claim that the pinned
100M YAML as written reproduces v4's 1.3B/100B training schedule.

## Frozen TS-1 workload and compute gate

TS-1 contains three paired seeds of GPT and NextLat-d=1. Per base run:

```text
tokens_per_update = 256 effective batch * 256 sequence = 65,536
base_tokens_per_run = 100,000 * 65,536 = 6,553,600,000
```

Across six base runs this is 600,000 optimizer updates and 39,321,600,000 packed
token exposures. Each frozen model then receives one 20-head probe run for 20,000
updates, adding 120,000 probe updates and 7,864,320,000 frozen-backbone token
forwards. Probe token forwards are stated separately because only the probe module
is optimized; counting them as full model-training tokens would overstate backward
compute.

Let `b_G`, `b_N` be measured base seconds/update and `p_G`, `p_N` measured probe
seconds/update. Let `c` terms be the corresponding checkpoint overhead fractions.
Then the aggregate accelerator time is

```text
TS1_GPU_hours =
    3 * 100000 * (b_G * (1+c_bG) + b_N * (1+c_bN)) / 3600
  + 3 *  20000 * (p_G * (1+c_pG) + p_N * (1+c_pN)) / 3600
  + measured_final_validation_GPU_hours
```

With one GPT queue and one NextLat queue on two GPUs, the base-plus-probe wall time
before validation is

```text
TS1_wall_hours = max(
  3 * (100000*b_G + 20000*p_G) / 3600,
  3 * (100000*b_N + 20000*p_N) / 3600
)
```

The following is arithmetic sensitivity, not a throughput estimate. It assumes the
two architecture queues have equal speeds and the current combined Vast rate is
`$0.302/hour`.

| base seconds/update | probe seconds/update | two-GPU wall time | rental at $0.302/h |
| ---: | ---: | ---: | ---: |
| 0.75 | 0.30 | 67.5 h | $20.39 |
| 1.50 | 0.60 | 135.0 h | $40.77 |
| 2.00 | 0.80 | 180.0 h | $54.36 |
| 3.00 | 1.20 | 270.0 h | $81.54 |

The required outcome-blind profile is 200 discardable base updates and 200
discardable probe updates per architecture. It may inspect only time, memory, batch
equivalence, compilation/precision, and checkpoint overhead. The full TS-1 launches
only if measured projection is at most **180 two-GPU wall-hours** and **USD 55** and
the user explicitly approves it. Exceeding either cap gives
`NO_LAUNCH_COMPUTE_CAP`; no shorter or one-seed scientific fallback is allowed.

TS-1 is not launch-ready because the pinned dataset snapshot has not been
downloaded/materialized, the exact packed-order receipt and single-GPU batch
equivalence are unimplemented, timing is unmeasured, and budget approval is absent.

## Frozen NL-1 workload

### Data footprint

- base unique tokens: 2.0B;
- retention tokens: 0.1B;
- two adaptation pools: 0.1B each;
- total pretokenized content: 2.3B GPT-2 tokens;
- uint16 token payload: approximately 4.6GB, before receipts, indexes, near-duplicate
  sketches, temporary download/cache, and safety margin;
- recommended persistent disk allocation: **at least 25GB**, because streaming,
  tokenization, manifests, checkpoints, and atomic staging coexist.

The official README warns that 100B pretokenization takes hours on many CPU cores.
NL-1 processes a much smaller subset but adds document hashing and duplicate audits.
A conservative preparation allowance is 4--12 CPU-hours, to be measured rather than
assumed.

### Training exposure

With effective batch 512 and sequence length 1,024:

- tokens/update = `524,288`;
- base updates/run = `3,814`;
- base exposure/run = `1,999,634,432` tokens;
- six base runs = `22,884` updates and `11,997,806,592` token exposures;
- 12 adaptation branches = `1,200` updates and `629,145,600` token exposures;
- total planned training = **24,084 optimizer updates and 12.627B token exposures**.

Evaluation and hidden-state extraction are forward-only and small relative to base
training. A standard dense-transformer approximation `6 * parameters * tokens`
places the six base runs near 7.2 exaFLOP at exactly 100M parameters, before NextLat
dynamics, optimizer work, padding, and evaluation. This number is an order check,
not a wall-clock estimator.

## Measured-profile contract

Run exactly 200 discardable updates for GPT and 200 for NextLat on the frozen base
stream. Do not log, open, or compare losses, CE, generations, hidden states, or
scientific metrics. Record only:

- seconds per optimizer update after the first 25 compile/warmup updates;
- peak allocated/reserved GPU memory;
- physical microbatch and gradient accumulation;
- checkpoint serialization/upload duration and size;
- accelerator model, CUDA/PyTorch versions, compilation and precision status.

Select the largest physical microbatch that fits from the fixed sequence
`[8, 4, 2, 1]`; gradient accumulation is respectively `[64, 128, 256, 512]` on one
GPU. Selection uses OOM/peak memory and throughput only. If microbatch 1 does not
fit, NL-1 is blocked on current hardware rather than width- or sequence-scaled.

Let `s_G` and `s_N` be measured steady-state seconds/update and `c_G`, `c_N` the
measured fractional checkpoint overheads. Then:

```text
aggregate_GPU_hours =
    3 * 3814 * (s_G * (1 + c_G) + s_N * (1 + c_N)) / 3600
  + 3 * 2 * 100 * (s_G + s_N) / 3600
  + measured_evaluation_GPU_hours
```

If one GPU runs the GPT queue and another runs the NextLat queue, a lower-bound wall
estimate is the larger queue:

```text
wall_hours >= max(
  3 * 3814 * s_G / 3600,
  3 * 3814 * s_N / 3600
) + branch/evaluation tail
```

## Why NL-1 is not launch-ready

1. FineWeb-Edu is not downloaded or revision-pinned locally.
2. The upstream pretokenizer cannot prove document-level base/retention/adaptation
   separation and must not be used unchanged.
3. The official configs target four GPUs; the 24GB single-GPU accumulation fallback
   is unprofiled.
4. No measured seconds/update, checkpoint overhead, or final dollar projection
   exists.
5. The user has not approved that measured incremental budget.

No GPU should be rented or kept idle specifically for NL-1 until these blockers are
cleared. Clearing them does not authorize inspecting existing scientific outcomes.

## Launch/no-launch decision rule

After the profile, create an immutable feasibility receipt with the measured total
wall time and cost. The complete frozen three-seed-pair NL-1 may launch only when
the measured projection is at most **120 wall-hours and USD 35 incremental rental**
and the user explicitly approves it. If either ceiling is exceeded, record
`NO_LAUNCH_COMPUTE_CAP`. There is no reduced scientific fallback within NL-1. A
one-seed run may be used only as an engineering shakeout; its scientific outputs
remain unopened and it cannot appear as external-validity evidence. Changing tokens,
seeds, context, model width, or update count requires a new numbered study.

## Bottom line

The two layers answer different objections. TS-1 provides a direct, focused bridge
to v4's TinyStories future-token result but remains model-generated language and
does not study forgetting. NL-1 supplies filtered real-world web English and a
genuine continued-pretraining intervention, but its proximity predictor is
observational and its 100M-class/2B-token scale does not match v4's
1.3B-parameter/100B-token evidence. Together they are credible triangulation, not
exact predictive-state ground truth or a matched-scale replication.

The program is required for the full external-validity/workshop claim but is not an
unconditional authorization to spend compute. TS-1 and NL-1 each remain blocked
until its frozen measured profile fits its own cap and the user approves it. There
is no outcome-selectable reduced design and no cross-arm rule that lets a positive
result compensate for a missing or null study.
